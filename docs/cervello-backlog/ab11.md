## End-state misurabile

Quando il selector canary gira per un workflow UI-touch jobRunner-bound (`invite`/`message`/`check`/`all`), la sessione browser del canary per l'account operativo viene RIUSATA dal jobRunner invece di chiudere+rilanciare sullo stesso profilo persistente (doppio lancio ravvicinato = lock conflict + pattern open/close detectabile). Zero regressioni: tutti i path di blocco chiudono la sessione, rotazioni interne invariate, `npm run conta-problemi` exit 0, antiban-review SICURO.

## Design raffinato 2026-06-13 (dopo lettura codice reale — 3 modifiche vs design originale)

1. **Proxy coherence — Opzione B (guard deriva da config), NON campo esterno.** jobRunner lancia con `preferredProxyType: config.proxyMobilePriorityEnabled ? 'mobile' : undefined` (`jobRunner.ts:194`). Il canary deriva lo STESSO valore da config quando riusa (single source = config, niente `reusePreferredProxyType` passato dall'orchestrator → zero rischio di divergenza caller/jobRunner).
2. **Handoff SOLO single-account.** Il loop canary fa `return {ok,session}` al primo handoff → con multi-account salterebbe la verifica degli account successivi (regressione canary). Quindi: handoff attivo solo se `accounts.length === 1` (caso dominante); multi-account → reuseAccountId undefined → canary verifica tutti = comportamento INVARIATO. (sync-list con `accountId` esplicito resta invariato.)
3. **Ownership via `handoffGuard` object nel try/finally ESISTENTE di `runWorkflow`** — NON estrazione funzione né re-indent di 400 righe. `runWorkflow` ha già `try/finally` (override account): aggancio lì la chiusura. `runWorkflowInternal(options, handoffGuard)` setta `handoffGuard.session` dopo il guard e la azzera dopo aver consegnato a `runQueuedJobs`. Ogni return di blocco intermedio → finally di `runWorkflow` chiude.
4. **Abort handoff prima dei satelliti intermedi.** Tra guard e `runQueuedJobs` ci sono 2 punti che aprono un browser sullo STESSO profilo: `LOW_ACTIVITY` random-activity (`orchestrator.ts:564`) + maturity warm-up (`:602`). Se la sessione handoff è aperta lì → lock conflict che fa fallire il warm-up anti-ban. → helper `releaseHandoff()` (disable+close+azzera) chiamato all'inizio di entrambi i blocchi. Casi rari (risk LOW_ACTIVITY / cookie <2gg) → comportamento attuale invariato; caso dominante (no satellite) → handoff pulito.
5. `enableWindowClickThrough` è idempotente (Set `_activePids`) → doppio enable canary+jobRunner sullo stesso PID sicuro (verificato `windowInputBlock.ts:206-223`).
